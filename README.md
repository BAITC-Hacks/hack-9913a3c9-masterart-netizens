# Граф денег

## 1. Название проекта

«Граф денег» — решение финансового кейса HackAlem AI. Команда Masterart Netizens.

## 2. Краткое описание

Инструмент для специалиста банковского финансового мониторинга: определить, какие счета из
предоставленного транзакционного графа проверить первыми, и показать основания для проверки.
Результат анализа — проверяемая гипотеза о роли счёта, а не утверждение о виновности клиента.

## 3. Что реализовано

**Промежуточный этап: разбор задания и проектирование.** В репозитории зафиксированы
[контракт входных и выходных данных](docs/case-contract.md), обязательные проверки и
[схема решения](docs/architecture.md). Аналитический конвейер и интерфейс ещё не реализованы;
готовность прототипа и качество классификации не заявляются.

## 4. Как работает

Планируемый основной сценарий: три исходных файла parquet → проверка данных → метрики направленного
графа → объяснимые роли, кластеры и приоритеты → три CSV-файла и локальный просмотрщик.
Аналитик выбирает счёт по `gid`, видит связи и основания вывода, затем формирует список для проверки.

## 5. Технологии

На этом этапе опубликована документация в Markdown и схема Mermaid. Для аналитики предусмотрен
Python; конкретные зависимости будут зафиксированы вместе с исполняемым кодом. Внешняя языковая
модель может быть отдельной необязательной функцией: обязательный результат не должен зависеть
от платного сервиса, облачного кластера или графического ускорителя.

## 6. Архитектура

См. [схему компонентов и границы достоверности](docs/architecture.md). Данные и вычисленные факты
служат единым источником для CSV-файлов и интерфейса. Текстовое объяснение не создаёт новых фактов.

## 7. Установка и запуск

Команда запуска приложения появится после реализации конвейера. Сейчас репозиторий содержит
проектную документацию; выдавать её за работающий прототип нельзя. Исходные файлы данных
предоставляют организаторы; в этот промежуточный коммит они не включены.

## 8. Как проверить

Проверяемый результат этого этапа — соответствие документации
[опубликованному заданию](https://docs.google.com/document/d/1JPLU-G6R25Ge2hVaY2J9cqvrx7FGExj87XKwJPaMz3o/edit).

| Результат | Проверка | Состояние |
|---|---|---|
| Контракт файлов и пяти обязательных функций | Сопоставить с разделами 5–7 задания | Описан |
| Схема решения | Проследить путь от parquet до выгрузок и интерфейса | Описана |
| Полный пересчёт, роли, кластеры и поиск по `gid` | Запустить будущую команду и автоматические проверки | Ещё не реализованы |

## 9. Данные и интеграции

По заданию: 2 248 узлов, 3 119 рёбер и 4 840 транзакций за июль 2026 года; 81 исходный клиент.
Используются только обезличенные данные организаторов. Внешнее обогащение сведений о клиентах
не предусмотрено. Все идентификаторы должны сохраняться без округления.

## 10. Ограничения

Выгрузка содержит только исходящие внутрибанковские переводы от исходных клиентов на глубину
четыре перехода, с порогом 5 000 тенге. Отсутствие дальнейших переводов на границе выгрузки
не доказывает, что деньги остались на счёте. Полный баланс, личность клиента, точное происхождение
средств и внутридневной порядок операций из этих данных не определяются. Размеченных ролей нет.

При росте до миллиона узлов потребуется пересмотреть хранение и вычисления: компактный формат
связей, пакетная обработка, предварительно рассчитанные метрики и загрузка только нужной
окрестности в интерфейс. Это направление развития, а не проверенный результат масштабирования.
