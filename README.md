# Граф денег

## 1. Название проекта

«Граф денег» — решение финансового кейса HackAlem AI. Команда Masterart Netizens.

## 2. Краткое описание

Инструмент для специалиста банковского финансового мониторинга: определить, какие счета из
предоставленного транзакционного графа проверить первыми, и показать основания для проверки.
Результат анализа — проверяемая гипотеза о роли счёта, а не утверждение о виновности клиента.

## 3. Что реализовано

**Промежуточный этап: аналитическое ядро работает; интерфейс в разработке.** Реализованы проверка
исходных parquet, метрики, объяснимые роли с альтернативами, приоритет проверки, кластеры и три
обязательные выгрузки. Временной модуль различает структурные связи, цепочки со строго более
поздними датами и возможный порядок внутри дня. Для датированных цепочек сохраняется проверяемый
пример из исходных транзакций. Интерфейс и AI-ассистент ещё не готовы.

На предоставленных данных полный конвейер завершился за **0,688 с** на проверенной машине:
2 248 счетов, 3 119 рёбер, 4 840 транзакций, 92 кластера. Это время вычисления, без установки
зависимостей. Точность обнаружения преступной деятельности не заявляется: эталонных ролей нет.

## 4. Как работает

Работающий сценарий: три исходных файла parquet → проверка данных → метрики направленного
графа → объяснимые роли, кластеры и приоритеты → три CSV-файла и `analysis.json`.
Следующий этап — просмотрщик: выбор счёта по `gid`, связи, основания вывода и список для проверки.

## 5. Технологии

Python 3.12, pyarrow 25.0.0, NetworkX 3.6.1; автоматические проверки на unittest.
Документация — Markdown, схема — Mermaid. React и TypeScript используются в разрабатываемом
интерфейсе. OpenAI-ассистент планируется отдельным слоем над проверяемыми операциями чтения графа;
аналитический результат не зависит от ключа модели, облачного кластера или GPU.

## 6. Архитектура

См. [схему компонентов и границы достоверности](docs/architecture.md). Данные и вычисленные факты
служат единым источником для CSV-файлов и интерфейса. Текстовое объяснение не создаёт новых фактов.

## 7. Установка и запуск

Требуется Python 3.12. Разместите три файла организаторов в `data/`.

```bash
python3 -m venv .venv
. .venv/bin/activate
python -m pip install pyarrow==25.0.0 networkx==3.6.1
python -m backend --data data --out out
```

Конвейер создаёт `nodes_roles.csv`, `clusters.csv`, `top_nodes.csv`, `analysis.json` и отдельную
квитанцию `run_receipt.json`. На проверенной машине зависимости уже были установлены; запуск
после установки в новом окружении ещё предстоит проверить. Единая команда запуска с интерфейсом
разрабатывается. Исходные данные не включены в Git: они выдаются организаторами.

## 8. Как проверить

Выполните после установки зависимостей:

```bash
FINANCE_DATA=data FINANCE_DATA_DIR=data python -m unittest discover -s tests -v
```

На объединённом ядре выполнена **51 проверка, все прошли**, включая официальные данные.
Без переменных с путём к данным соответствующие проверки явно пропускаются, что не считается
подтверждением полного набора. Контракт сверяется с
[опубликованным заданием](https://docs.google.com/document/d/1JPLU-G6R25Ge2hVaY2J9cqvrx7FGExj87XKwJPaMz3o/edit).

| Функция | Проверка | Состояние |
|---|---|---|
| `core` — валидация, роли, приоритеты, кластеры и выгрузки | `tests/test_core.py`: положительные и отрицательные примеры, точные идентификаторы и суммы, повторяемость | 28 проверок прошли |
| `TEMP` — временная достижимость и примеры цепочек | `tests/test_temporal.py`: обратные даты, порядок внутри дня, циклы, независимые эталоны, реальные транзакции | 23 проверки прошли |
| Интерфейс и поиск по `gid` | Проверка в настоящем браузере | В разработке |
| OpenAI-ассистент | Реальный запрос через модель и проверяемые операции графа | Интеграция в приложение ещё не проверена |

Пороги и их объяснения находятся в `backend/policy.py`. Все роли — гипотезы; `role_score`
обозначает поддержку правила, а не вероятность виновности. Приоритет рассчитывается отдельно
из пяти раскрытых семейств признаков. Кластеры строятся Louvain с фиксированным зерном на явно
неориентированной проекции; направления переводов сохраняются в исходном графе и выгрузке.

## 9. Данные и интеграции

По заданию: 2 248 узлов, 3 119 рёбер и 4 840 транзакций за июль 2026 года; 81 исходный клиент.
Используются только обезличенные данные организаторов. Внешнее обогащение сведений о клиентах
не предусмотрено. Все идентификаторы должны сохраняться без округления.

## 10. Ограничения

Выгрузка содержит только исходящие внутрибанковские переводы от исходных клиентов на глубину
четыре перехода, с порогом 5 000 тенге. Отсутствие дальнейших переводов на границе выгрузки
не доказывает, что деньги остались на счёте. Полный баланс, личность клиента, точное происхождение
средств и внутридневной порядок операций из этих данных не определяются. Размеченных ролей нет.

При росте до миллиона узлов потребуется пересмотреть хранение и вычисления: компактный формат
связей, пакетная обработка, предварительно рассчитанные метрики и загрузка только нужной
окрестности в интерфейс. Это направление развития, а не проверенный результат масштабирования.
